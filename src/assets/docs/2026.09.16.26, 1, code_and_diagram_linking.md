The editor and preview only share the source string. The left pane writes `mermaidSettings.source`; the right pane re-renders after a 300 ms debounce and injects the SVG with `dangerouslySetInnerHTML`. There is no cursor tracking, no node click handler, and no source map.

What makes this feasible is that `beautiful-mermaid` already stamps semantic IDs onto the SVG:

| Diagram | Clickable element | Attributes |
|---|---|---|
| Flowchart | `g.node`, `g.subgraph`, `polyline.edge` | `data-id`, `data-from` / `data-to` |
| Sequence | `g.actor`, `g.message` | `data-id`, `data-from` / `data-to` |
| Class | `g.class-node` | `data-id` |
| ER | `g.entity` | `data-id` |

So a click on a box already tells you *which* node it is (`A`, `CUSTOMER`, `Alice`). The missing piece is mapping that ID to a line in the editor, and the reverse.

## Why there is no real source map

`parseMermaid` (and the other parsers) do not keep line or column. They also drop blank lines and `%%` comments before parsing, so a parser index would not match the editor anyway. Official Mermaid is the same: no first-class “this node came from line 4.”

You do not need a true AST source map for a useful link. Node IDs are unique enough to search in the original source.

## How the two directions would work

**Diagram → editor (click a block, jump to the line)**  
1. Listen on the preview container (`closest('.node, .subgraph, .actor, .class-node, .entity, .edge, .message')`).  
2. Read `data-id` (or `data-from` / `data-to` for an edge).  
3. Search the source with a Mermaid-aware identifier regex so `A` does not match `A1` or `Start`. Prefer the first *definition* (`A[Start]`, `A{...}`) over a later `A --> B`.  
4. Use a Monaco instance from `onMount`: `revealLineInCenter`, `setSelection`, and a whole-line decoration.

That needs an editor ref. Today the Monaco wrapper is only `value` / `onChange`.

**Editor → diagram (cursor moves, highlight the box)**  
1. `onDidChangeCursorPosition` → parse IDs on the current line.  
2. `svg.querySelectorAll('[data-id="A"]')` (and edges that mention that ID).  
3. Toggle a CSS class on those groups. A one-line `A --> B --> C` should highlight all three.

Shared valtio state such as `selectedNodeIds: string[]` is enough; both panes already read from that store.

## Caveats

- **One ID, many lines.** `A` can be declared once and reused on several edges. Jump to the definition line; optionally underline every occurrence.  
- **One line, many IDs.** Highlight every mentioned node.  
- **Pan mode** already captures pointer events. Treat a click as a selection only if the pointer barely moved.  
- **ASCII output** has no DOM nodes. Skip linking in that mode.  
- **XY charts** are series/axes, not named boxes; linking is much weaker.  
- **CSS.** The SVG is themed with variables inside the `<svg>`. Put highlight styles on a wrapper around the injected markup (for example `.preview-svg .node.is-selected > rect { stroke: ... }`), not inside the library.

A later, more precise version would wrap or fork the parsers to record `{ id, line, column, endLine }` as they scan. That is nicer for edges and `linkStyle 0`, but not required for “click this box, go to that line.”

So: bidirectional linking is a UI feature on top of IDs the renderer already emits. The practical first slice is SVG-only, flowchart-first, heuristic ID search plus Monaco decorations. I can sketch or implement that if you switch to Agent mode.

**How it behaves**
- Click a block or connector in the SVG → that line is selected in Monaco (strong highlight).
- Move the caret → matching SVG elements get a soft highlight.
- Click a line in the editor → strong highlight, and the preview scrolls to the match.
- ASCII / Text output does nothing. Pan mode still selects on a click; a drag does not.
