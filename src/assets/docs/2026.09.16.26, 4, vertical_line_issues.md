**Broken vertical lines (`index.ts`)**  
That node is a subroutine (`[[index.ts]]`). The inner bars are separate `<line>` elements from the top edge to the bottom edge:

```434:444:node_modules/beautiful-mermaid/src/renderer.ts
function renderSubroutine(x: number, y: number, w: number, h: number, fill: string, stroke: string, sw: string): string {
  const inset = 8
  return (
    `<rect x="${x}" y="${y}" width="${w}" height="${h}" ... />` +
    `\n<line x1="${x + inset}" y1="${y}" x2="${x + inset}" y2="${y + h}" ... />` +
    `\n<line x1="${x + w - inset}" y1="${y}" x2="${x + w - inset}" y2="${y + h}" ... />`
  )
}
```

They do not join the outer rectangle. Stroke is 0.75px, so at the T-junctions you get a gap or a small overlap. The incoming arrow also sits on the left inner bar, which makes that one look interrupted.

Official Mermaid avoids this by drawing the outer box and inner bars as one closed path, so the corners actually join.

Vendoring can make sense here, but I would not drop the library into `src/` as an app module. A workspace copy is the right shape if you expect more renderer or layout work. There are lighter options that are a better first step.

This app only uses a small public surface: `renderMermaidSVG`, `renderMermaidASCII`, `THEMES`, `DEFAULTS`, and a few types. The rest of `beautiful-mermaid` (ASCII, sequence, class, ER, xychart, the FakeWorker ELK hack) stays behind that API. Vite already treats `beautiful-mermaid` + `elkjs` + `entities` as one lazy chunk.

**On ELK:** adding `elkjs` to this app’s `package.json` is good hygiene. It does **not** give you an independent layout engine. `beautiful-mermaid` imports `elkjs/lib/elk.bundled.js` and talks to FakeWorker internals (`dispatcher.saveDispatch`) to force synchronous layout. That coupling is pinned to ELK 0.11.x. A direct dependency lets you pin, audit, and dedupe the 1.6 MB engine; it does not let you swap ELK versions or call ELK yourself unless you also own `elk-instance.ts`.

---

**Options, lightest first**

1. **`pnpm patchedDependencies`**  
   Keep `beautiful-mermaid@1.1.3` from npm. Patch `renderer.ts` for the subgraph header and subroutine bars.  
   Best for the two stroke bugs. Lowest cost. You still do not own ELK.

2. **Direct `elkjs` + `pnpm.overrides`** (can combine with 1)  
   Add `elkjs` next to `monaco-editor` the same way: you rely on it, so declare it. Override so there is one copy.  
   This matches the scheduling/audit concern. It does not change how layout runs.

3. **Git URL / GitHub fork**  
   Depend on `github:lukilabs/beautiful-mermaid#<commit>` or your fork. You can pick up unreleased work (for example [PR #98](https://github.com/lukilabs/beautiful-mermaid/pull/98) on nested subgraphs) without copying the tree. ELK stays transitive unless the fork makes it a peer.

4. **pnpm workspace package (the “clone it here” version I would use)**  
   Copy the **npm `src/`**, not the whole GitHub repo (that repo is also the vanilla editor, Bun tests, Wrangler). Something like:

   ```
   packages/beautiful-mermaid/   # workspace package, MIT, elkjs as its own dependency
   src/                          # this app, still imports 'beautiful-mermaid'
   ```

   Then `"beautiful-mermaid": "workspace:*"` and `elkjs` as a real dependency of that package (and of the app if you want it visible at the root). You keep the current `import('beautiful-mermaid')` lazy load. You can fix strokes, header drawing, and later ELK options without waiting on npm.

5. **Post-process the SVG in `renderDiagram`**  
   Do not fork. After `renderMermaidSVG()`, tweak header rects and subroutine lines. Fragile, and it does nothing for ELK.

I would **not** inline the library under `src/components` or `src/vendor` as loose files. You lose the package boundary, the Vite chunk test (`node_modules/beautiful-mermaid|elkjs`) stops matching unless you rewrite it, and app code starts mixing with a ~80-file renderer.

---

**When vendoring is worth it**

Do it if you expect more than a one-off stroke patch: subgraph layout, edge routing, ELK options, or you want `elkjs` as a first-class dep with the FakeWorker wrapper in-tree.

Stay on npm + a pnpm patch if the next six months are “fix two SVG glitches and otherwise leave the engine alone.”

A practical sequence: **patch now**, add **`elkjs` as a direct dep + override**, and only workspace-vendor if the next layout bug appears or you want to change ELK usage. Cloning first is reasonable too, given how slowly that package moves; just clone it as a package, not as app source.
